凌晨两点，告警：`cn-192-168-3-50 NotReady`。上面跑着十几个业务 Pod。

`NotReady` 是个信息量很低的状态 —— 它只说明 kubelet 停止上报心跳了，可能的原因有十几种。这一关练的是**用固定顺序收敛**，而不是凭直觉挨个试。

## 排查顺序：从外向内四层

```
第 1 层  控制面视角     kubectl get/describe node  —— 集群知道什么
第 2 层  节点侧 kubelet  systemctl status / journalctl —— kubelet 自己怎么说
第 3 层  运行时与资源    crictl / df / free —— 底下的东西还活着吗
第 4 层  网络与证书      到 apiserver 的连通性 —— 心跳发得出去吗
```

顺序的意义是**每一层都能排除掉一批可能**。跳着查最容易漏掉真正的原因。

## 根因链

```
系统盘只有 200G，且 containerd 镜像目录与系统盘共用
   ↓
镜像层累积到 142G + 容器日志 48G 未限制大小
   ↓
磁盘 100% 满
   ↓
kubelet 触发 DiskPressure，尝试回收镜像但只释放了 100MB（正在用的镜像删不掉）
   ↓
containerd 写不了自己的元数据，CRI 调用超时
   ↓
kubelet 无法同步 Pod、无法 patch node status、无法更新 lease
   ↓
心跳停止 → 控制面标记 NotReady → 打上 unreachable 污点 → Pod 开始驱逐
```

注意这个故障的形状：**kubelet 进程一直活着**，它只是干不了活。如果第一反应是 `systemctl restart kubelet`，重启完照样 NotReady，而且浪费了时间。

## 处置

```bash
# 1. 先止血：清掉最大的可回收项 —— 已停止容器的日志
ssh cn-192-168-3-50 'find /var/log/pods -type f -name "*.log" -mtime +7 -delete'

# 2. 清理未被使用的镜像
ssh cn-192-168-3-50 'crictl rmi --prune'    # containerd 恢复响应后才能执行

# 3. containerd 恢复后 kubelet 会自动恢复上报，节点回到 Ready
kubectl get node cn-192-168-3-50 -w

# 4. 确认 Pod 恢复；redis-0 这类单副本有状态服务要单独核对数据
kubectl get pod -A -o wide --field-selector spec.nodeName=cn-192-168-3-50
```

<Callout type="warn" title="磁盘满的节点，重启 kubelet 或 containerd 都没用">
两个进程都需要写盘才能工作。盘满的情况下重启它们，只是让它们在启动阶段就失败 —— 而且可能让原本还能读的元数据变成损坏状态。

**先腾空间，再考虑重启服务。** 顺序反了会把「节点不可用」变成「节点需要重装」。
</Callout>

## 治本

这次故障暴露的是三个配置缺失：

```toml
# 1. 限制容器日志大小 —— /etc/containerd/config.toml
[plugins."io.containerd.grpc.v1.cri".containerd]
  # 每个容器日志最大 100MB，保留 3 个文件
  max_container_log_line_size = 16384
```

```yaml
# 2. kubelet 侧配足预留与镜像回收阈值
# /var/lib/kubelet/config.yaml
kubeReserved:
  ephemeral-storage: 20Gi
evictionHard:
  nodefs.available: "10%"
  imagefs.available: "15%"
imageGCHighThresholdPercent: 80      # 到 80% 就开始回收，不要等到告急
imageGCLowThresholdPercent: 70
```

```bash
# 3. 把镜像与日志目录挪到数据盘（这次故障的根本原因）
mkdir -p /data/containerd /data/kubelet
# 通过 bind mount 挂到标准路径，写进 fstab
echo "/data/containerd /var/lib/containerd none defaults,bind 0 0" >> /etc/fstab
echo "/data/kubelet /var/lib/kubelet none defaults,bind 0 0" >> /etc/fstab
```

<Callout type="tip" title="把磁盘水位做成告警，这是最划算的一条">
`DiskPressure` 出现在 NotReady **之前 4 分钟**。也就是说这次故障有 4 分钟的预警窗口，只是没人看。

```promql
# 节点文件系统使用率超过 80%
(1 - node_filesystem_avail_bytes{mountpoint="/"} / node_filesystem_size_bytes{mountpoint="/"}) > 0.8

# 直接抓 kubelet 上报的 DiskPressure condition
kube_node_status_condition{condition="DiskPressure",status="true"} == 1
```
第二条尤其值得配 —— 它是 kubelet 自己的判断，比阈值猜测更准。
</Callout>

## NotReady 的完整排查清单

这一关走的是磁盘那条路。其它常见原因按同样的四层顺序排：

| 层 | 检查 | 命令 |
| --- | --- | --- |
| 1 | 是一台还是一批 | `kubectl get node` |
| 1 | Conditions 与 Events | `kubectl describe node` |
| 1 | 影响面 | `get pod -o wide --field-selector spec.nodeName=` |
| 2 | 机器是否活着（**有状态服务必查**） | `ssh` / IPMI / BMC |
| 2 | kubelet 进程与日志 | `systemctl status kubelet`、`journalctl -u kubelet` |
| 3 | 磁盘 | `df -h`、`du -sh /var/lib/containerd /var/log/pods` |
| 3 | 内存与 OOM | `free -h`、`dmesg -T \| grep -i oom` |
| 3 | 运行时 | `crictl ps`、`systemctl status containerd` |
| 4 | 到 apiserver 的连通性 | `curl -k https://<vip>:6443/healthz` |
| 4 | 证书是否过期 | `openssl x509 -in /var/lib/kubelet/pki/kubelet-client-current.pem -noout -dates` |
| 4 | 时间偏差 | `timedatectl status` |

对应关系（看到什么想到什么）：

| 现象 | 指向 |
| --- | --- |
| kubelet 进程已死 | 配置错误、OOM、二进制损坏 |
| kubelet 活着但报 `context deadline exceeded` | **运行时无响应** —— 通常是磁盘 |
| kubelet 报 `Unauthorized` | **证书过期**或时间偏差 |
| kubelet 报连接超时 | 到 apiserver 的网络、VIP 漂移 |
| ssh 不通、IPMI 显示已关机 | 真宕机，可以删 Node 对象 |
| ssh 不通但 IPMI 显示在运行 | **可能是网络分区，有状态服务不要贸然删 Node** |

## 这一关的收获

- **固定四层顺序**：控制面 → kubelet → 运行时与资源 → 网络与证书，每层排除一批可能
- `describe node` 的 Conditions 里往往写着 NotReady **之前**发生了什么 —— 那才是根因
- **kubelet 活着但不上报**，指向下游（运行时、磁盘、网络），不要盲目重启
- 磁盘满时**先腾空间再重启服务**，反了会把不可用变成需要重装
- 处置之前先看影响面，单副本有状态服务要区别对待
- 这类故障几乎都有预警窗口，`DiskPressure` + 使用率 + 趋势三层监控就能抓住
