「每个团队一套集群」和「所有团队一套集群」之间，还有一整排折中方案。

选错的代价是双向的：隔离过度，运维成本乘以团队数；隔离不足，一个团队的失误会影响所有人。

## 隔离强度谱系

```
弱 ←────────────────────────────────────────────────→ 强
运维成本低                                        运维成本高

命名空间   +NetworkPolicy   虚拟集群      独立集群
+RBAC      +ResourceQuota   (vcluster/    (物理隔离)
                             Kamaji/k3k)
```

| 方案 | 隔离了什么 | 没隔离什么 | 运维成本 |
| --- | --- | --- | --- |
| 命名空间 + RBAC | API 权限 | 网络、资源、CRD、节点 | 极低 |
| + NetworkPolicy + Quota | 再加网络与资源额度 | **CRD、集群级权限、控制面** | 低 |
| 虚拟集群 | **控制面、CRD、集群级权限** | 内核、节点（共享） | 中 |
| 独立集群 | 全部 | — | 高 |

<Callout type="warn" title="判断标准：租户需要集群级权限吗">
选型不该按「感觉需要多强的隔离」，而该问一个具体问题：**这个租户需要装自己的 CRD、或者需要集群级权限吗？**

- **不需要** → 命名空间 + RBAC + NetworkPolicy + Quota 就够了，别上虚拟集群
- **需要** → 命名空间方案根本做不到（CRD 是集群级资源，一个租户装的 CRD 全集群可见），必须上虚拟集群

这个问题一问，大部分场景的选择就定了。常见的「需要」场景：租户自己要装 Operator、要用不同版本的 CRD、要给自己的 CI 发 cluster-admin。
</Callout>

## 命名空间方案：三件套

这是绝大多数场景的答案，三样东西一起配才成立：

```yaml
# 1. RBAC：API 权限（L1《认证授权》）
#    ClusterRole edit + 限定在该命名空间的 RoleBinding

# 2. NetworkPolicy：网络隔离（L3《网络策略》）
#    default-deny + 按需放行，别忘了 DNS

# 3. ResourceQuota + LimitRange：资源额度
apiVersion: v1
kind: ResourceQuota
metadata: { name: team-a-quota, namespace: team-a }
spec:
  hard:
    requests.cpu: "200"
    requests.memory: 800Gi
    requests.nvidia.com/gpu: "16"
    persistentvolumeclaims: "50"
    requests.storage: 10Ti
    count/deployments.apps: "100"
    pods: "500"
---
apiVersion: v1
kind: LimitRange
metadata: { name: team-a-defaults, namespace: team-a }
spec:
  limits:
    - type: Container
      default:                    # 没写 limits 时的默认值
        cpu: "1"
        memory: 2Gi
      defaultRequest:             # 没写 requests 时的默认值
        cpu: 100m
        memory: 256Mi
      max:
        cpu: "32"
        memory: 256Gi
```

<Callout type="tip" title="LimitRange 兜住了「忘配 requests」这个问题">
L1《调度器》讲过：不设 requests 的 Pod 是 BestEffort，会让集群的容量规划变成假的 —— `describe node` 显示只分配了 30%，节点却随时可能 OOM。

`LimitRange` 的 `defaultRequest` 让漏配的 Pod 自动获得一个合理的 requests，从根上避免 BestEffort 泛滥。

**每个租户命名空间都应该配 LimitRange**，这是成本最低、收益最直接的一条治理措施。
</Callout>

<Callout type="warn" title="ResourceQuota 一旦设置，所有 Pod 必须声明对应资源">
这是个容易踩的坑：`ResourceQuota` 里写了 `requests.cpu`，那么该命名空间下**所有** Pod 都必须声明 `requests.cpu`，否则创建直接被拒绝：

```
Error: pods "web-xxx" is forbidden: failed quota: team-a-quota:
must specify requests.cpu
```

配合 `LimitRange` 的 `defaultRequest` 就能自动补上，两者是配套使用的。只配 Quota 不配 LimitRange，会让业务方一堆清单突然报错。
</Callout>

## 虚拟集群：三种实现

当租户需要自己的控制面时，有三个方案：

| 方案 | 控制面在哪 | 数据面 | 特点 |
| --- | --- | --- | --- |
| **vcluster** | 宿主集群里的一个 Pod（k3s/k8s） | **Pod 同步到宿主集群** | 最轻，生态成熟 |
| **Kamaji** | 宿主集群里的 Pod，**etcd 多租户复用** | 真实的 worker 节点加入 | 控制面即 Pod，适合大量集群 |
| **k3k** | 宿主集群里的 k3s | 可选虚拟或真实节点 | 轻量，k3s 生态 |

### vcluster 的工作方式

```
宿主集群
├─ namespace: vcluster-team-a
│   ├─ Pod: vcluster-0            ← 里面跑着 k3s（apiserver + controller + scheduler）
│   ├─ Pod: coredns-xxx
│   └─ Pod: team-a-web-xxx-x      ← 租户的 Pod 被【同步】到这里，加了前缀
```

租户在自己的虚拟集群里看到的是一套完整的 K8s：可以装 CRD、可以有 cluster-admin、可以建任意命名空间。而 syncer 把真正需要跑的 Pod 同步到宿主集群的一个命名空间里执行。

```bash
vcluster create team-a --namespace vcluster-team-a
vcluster connect team-a          # 拿到虚拟集群的 kubeconfig
kubectl get ns                   # 看到的是虚拟集群自己的命名空间
```

<Callout type="note" title="虚拟集群隔离的是控制面，不是内核">
这一点必须对租户说清楚，否则会有错误的安全预期。

**隔离的**：apiserver、etcd、CRD、集群级 RBAC、命名空间视图

**没隔离的**：
- **内核** —— 所有 Pod 仍然共享宿主机内核，容器逃逸的风险不变
- **节点资源** —— 虚拟集群的 Pod 和其它租户的 Pod 抢同一批节点
- **CNI / CSI** —— 用的还是宿主集群的网络和存储

所以虚拟集群不是安全边界，是**管理边界**。真需要安全隔离（不可信代码、合规要求）得上独立集群，或者用 Kata Containers 这类内核级隔离方案。
</Callout>

### Kamaji：控制面即 Pod

Kamaji 的思路更彻底：把**多个租户集群的控制面**都跑成宿主集群里的 Deployment，并让它们**共享一套 etcd**（通过数据前缀隔离）。

```
管理集群（Kamaji 运行在这里）
├─ TenantControlPlane: team-a     → Deployment（apiserver + controller + scheduler）
├─ TenantControlPlane: team-b     → Deployment
└─ 共享的 etcd 集群（多租户，按前缀隔离）

真实的 worker 节点 → join 到对应租户的控制面
```

适合的场景是**要管理很多个集群**：每个租户集群的控制面只是几个 Pod，不需要三台专用管理节点。相比每套集群都配 3 台控制面，硬件成本差距巨大。

代价是共享 etcd 成了单点 —— 它出问题会影响所有租户集群。

<Callout type="tip" title="怎么选这三个">
- **vcluster** —— 租户只需要一个「看起来像集群」的开发/测试环境，不需要真实节点。最省事
- **Kamaji** —— 要交付**很多套真集群**（比如给多个部门各一套生产集群），且想省下控制面的硬件成本
- **k3k** —— 场景类似 vcluster，团队已经在用 k3s 生态时更顺手

判断关键：**租户需要自己的真实 worker 节点吗？** 需要 → Kamaji；不需要 → vcluster。
</Callout>

## GPU 集群的多租户特殊性

GPU 让多租户问题变得更尖锐，因为**卡不可超卖**（L1《调度器》讲过）：

```yaml
# ResourceQuota 只能限制总量
requests.nvidia.com/gpu: "16"
```

但 Quota 解决不了两个 GPU 特有的问题：

| 问题 | 现象 | 解法 |
| --- | --- | --- |
| **卡被占着不用** | 一个交互式任务占 8 卡，人已经下班了 | 监控「已分配但利用率为 0」+ 强制 TTL |
| **配额内的排队不公平** | A 团队提交 100 个任务塞满队列，B 团队的小任务永远排不上 | Kueue 的队列 + 优先级 + 借用 |

<Callout type="warn" title="GPU 多租户靠 Kueue 而不是 ResourceQuota">
`ResourceQuota` 是**硬上限**：额度用完就拒绝创建，且**没用完的额度也不能借给别人**。

在 GPU 集群里这非常浪费：A 团队保底 32 卡但夜里不用，B 团队白天排队等卡 —— 两边都不满意，而卡在闲着。

L4《AI 负载调度》讲的 Kueue Cohort 借用机制才是对的工具：

```yaml
spec:
  cohort: shared-gpu
  resourceGroups:
    - flavors:
        - resources:
            - name: "nvidia.com/gpu"
              nominalQuota: 32       # 保底
              borrowingLimit: 32     # 空闲时最多再借 32
  preemption:
    reclaimWithinCohort: Any         # 自己要用时能收回来
```
**GPU 集群里 ResourceQuota 用来兜底防滥用，实际的资源分配交给 Kueue。**
</Callout>

## 成本对比

| 方案 | 硬件成本 | 运维成本 | 适合规模 |
| --- | --- | --- | --- |
| 命名空间三件套 | 零额外 | 低（策略模板化后基本零） | 任意 |
| vcluster | 每租户几个 Pod | 中（多一层要排障） | 十几个租户 |
| Kamaji | 每租户几个 Pod + 共享 etcd | 中高 | 几十套集群 |
| 独立集群 | **每套 3 台控制面** | 高（升级、监控、备份 ×N） | 少数强隔离需求 |

<Callout type="trap" title="独立集群的真实成本不是硬件">
「给每个团队一套集群」听起来干脆，但硬件只是账单的一小部分。真正的成本是：

- **升级 ×N** —— 每套集群都要走一遍 L2《集群升级》的完整流程
- **监控 ×N** —— 每套都要接监控、配告警、建面板
- **备份 ×N** —— 每套 etcd 都要备份并**定期演练恢复**
- **知识分散** —— 每套集群的配置漂移，最后没人说得清它们的差别

五套集群的运维负担远大于五倍单集群 —— 因为它们会逐渐变得不一样。

所以独立集群应该留给**真正需要物理隔离**的场景（合规、强不信任、不同网络域），而不是当作「隔离不够就再开一套」的默认答案。
</Callout>

## 这一节的落点

- 选型先问一个具体问题：**租户需要装自己的 CRD 或集群级权限吗**
- 不需要 → **命名空间三件套**（RBAC + NetworkPolicy + Quota/LimitRange），覆盖绝大多数场景
- **LimitRange 必配** —— 它兜住「忘配 requests」，也是 Quota 生效的前提
- 需要 → 虚拟集群：**要真实节点选 Kamaji，不要就选 vcluster**
- 虚拟集群是**管理边界不是安全边界**，内核仍然共享
- GPU 多租户靠 **Kueue 的 Cohort 借用**，ResourceQuota 只用来兜底
- 独立集群的真实成本是**升级/监控/备份 ×N 加配置漂移**，留给真正需要物理隔离的场景
