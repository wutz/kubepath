前面三十五节讲的都是「怎么做对一件事」。这一节讲怎么让做对的方法**留下来**。

把排查过程固化成 SOP、把每次事故变成一条检查项 —— 这是运维团队唯一的复利。人会走，SOP 会留下。

## 告警分级与响应

分级的意义是让人知道**什么时候必须放下手里的事**：

| 级别 | 判据 | 响应 | 每周数量目标 |
| --- | --- | --- | --- |
| **P1 critical** | 业务已受影响，或集群不可变更 | 立即呼人，任何时间 | **≤ 3 条** |
| **P2 warning** | 有余量但在恶化 | 值班时间处理 | ≤ 20 条 |
| **P3 info** | 趋势与容量类 | 只上看板，每周看 | 不限 |

<Callout type="warn" title="P1 的数量是告警质量的唯一硬指标">
如果每周有几十条 P1，值班的人会自然学会忽略它们 —— 然后真出事那条被淹掉。这是所有告警体系失效的共同路径。

判断标准很直接：**一条告警如果从来没人因为它做过任何事，它就该降级或删掉。**

每个季度做一次告警复盘：拉出这个季度所有 P1，逐条问「收到之后做了什么」。答不出来的就降级。这个动作比新增告警重要得多。
</Callout>

## SOP 该怎么写

一份能用的 SOP 有五个部分。以最常见的告警为例：

```markdown
## 告警：EtcdHighFsyncDuration

**含义**：etcd WAL fsync p99 超过 50ms，集群写入路径正在变慢。

**影响**：apiserver 写请求变慢；持续恶化会触发选主，导致集群短暂不可变更。
业务侧已运行的 Pod 不受影响（见 L1 的组件影响面对照表）。

**诊断**（按顺序，不要跳）：
1. 确认范围：三个 etcd 成员都慢，还是只有一个？
   `etcdctl endpoint status --write-out=table --cluster`
2. 看是否已在选主：`increase(etcd_server_leader_changes_seen_total[15m])`
3. 查该节点磁盘：`iostat -x 1`、`node_disk_io_time_seconds_total`
4. 确认 etcd 数据目录是否被别的东西占用了盘（日志、备份任务）
5. 查 DB 大小是否接近配额：`etcd_mvcc_db_total_size_in_bytes`

**处置**：
- 单成员慢 + 磁盘忙 → 找出抢盘的进程；必要时把该成员摘出集群维护
- 三成员都慢 + DB 接近配额 → 按《etcd 运维》做 compact + defrag（一台一台）
- 磁盘本身不达标 → 这是硬件问题，需要计划停机换盘，不要试图靠调参解决

**不要做**：
- 不要调 Raft 的心跳/选举超时参数来「消除」告警 —— 那是把症状盖住
- 不要三个成员同时 defrag —— 会一起阻塞，quorum 消失
```

关键是**「不要做」这一节**。SOP 的价值一半在于告诉人别做什么 —— 尤其是那些看起来能快速消除告警、实际上会让问题更糟的操作。

<Callout type="tip" title="SOP 里的每条诊断命令都要能直接复制运行">
写「检查磁盘性能」没用，写 `iostat -x 1` 才有用。凌晨三点的人不应该需要现场回忆命令参数。

同理，PromQL 要写完整、路径要写绝对路径、需要哪些权限也要写清。**SOP 的读者是半夜被叫起来、状态最差的自己。**
</Callout>

## 值班手册的骨架

按「症状」组织，而不是按「组件」—— 因为值班的人手里拿到的是症状：

| 症状 | 去哪一节 |
| --- | --- |
| kubectl 完全不可用 | 控制面故障（L1 组件影响面表 + L2 证书轮转） |
| 集群整体变慢 | etcd fsync → apiserver list → 控制面资源 |
| 一台节点 NotReady | L2《NotReady 闯关》的四层顺序 |
| 一批节点同时 NotReady | 网络、证书过期、时间偏差 |
| Pod Pending | L1《调度器》的节点淘汰统计 |
| Pod ContainerCreating | 镜像 / CNI / 存储挂载三条线 |
| Pod CrashLoopBackOff | `logs --previous` + exitCode |
| PVC Pending | L3《PVC 闯关》的八步清单 |
| Service 访问不通 | endpoints → DNS → NetworkPolicy → MTU |
| GPU 任务起不来 | 卡是否被隐形占用、Kueue 配额、fabric manager |
| 训练性能不达标 | 数据管道 → NCCL 传输路径 → 拓扑绑定 |

每一行链到一份具体的 SOP。这份索引本身就是值班手册的首页。

## 变更管理

生产事故里很大一部分是变更引起的。四条能落地的规则：

### 1. 变更窗口

```
低风险（加节点、扩副本）     随时
中风险（改配置、升级组件）    工作时间，避开业务高峰
高风险（升级集群、动 etcd、  维护窗口，提前通知，两人在场
       改网段、控制面变更）
```

### 2. 变更前检查清单

```markdown
- [ ] 影响面：哪些业务、哪些命名空间会受影响
- [ ] 回滚方案：**具体的命令**，不是「出问题就回滚」
- [ ] 回滚边界：从哪一步开始就没有真正的回滚了（见 L2《集群升级》）
- [ ] 备份：etcd 快照已打并【已验证】
- [ ] 通知：业务方已知晓时间窗口
- [ ] 验证方法：怎么确认变更成功（具体命令 + 预期输出）
- [ ] 双人复核：高风险变更必须有第二个人看过
```

<Callout type="trap" title="「出问题就回滚」不是回滚方案">
这是变更评审里最常见的空话。真正的回滚方案要能回答：

- **具体执行什么命令**
- **需要多长时间**
- **会不会丢数据**
- **从哪一步之后就没有回滚了**（L2《集群升级》讲的 etcd 单向门）

写不出这四点，说明这次变更的风险还没评估清楚 —— 那就还不能做。
</Callout>

### 3. 灰度顺序

```
测试集群 → 生产的一个节点 → 一批节点（3–5 台）→ 全量
        ↑ 每一步之间都要有【明确的验证】和【停下来的理由】
```

每一步的「停下来的理由」要提前写好：什么指标变化到什么程度就中止。不写的话，人在推进过程中会倾向于继续。

### 4. 变更留痕

```bash
# inventory、helmwave 配置、清单全部进 Git
git log --oneline inventory/mycluster/
```

L2 强调过：`inventory/` 是集群的唯一事实来源。变更走 PR 有三个额外好处 —— 有 review、有历史、能回答「上周谁改了什么」。

## 故障复盘

复盘的目标是**改进系统，不是追究个人**。这件事需要刻意维护，否则会自然退化成追责会。

```markdown
## 事故复盘：2026-08-19 节点 NotReady 导致部分服务中断

**影响**：14 个 Pod 被驱逐，web 服务容量下降 40%，持续 23 分钟。
**时间线**（用采集到的 Event 和监控数据还原，不靠记忆）
- 01:48  kubelet 首次报告 DiskPressure          ← 预警窗口从这里开始
- 01:52  节点转为 NotReady
- 02:10  值班收到 NotReady 告警                  ← 18 分钟后才有人知道
- 02:15  定位到磁盘满
- 02:33  清理日志，节点恢复

**根因**：镜像与容器日志目录在系统盘上，且未限制容器日志大小。
**为什么没有被提前发现**：没有配置磁盘水位告警和 DiskPressure 告警。

**改进项**（每条都有负责人和期限）
| 改进 | 类型 | 负责人 | 期限 |
| --- | --- | --- | --- |
| 配置磁盘水位 + DiskPressure 告警 | 检测 | @a | 8-22 |
| 限制容器日志大小与轮转 | 预防 | @b | 8-26 |
| 镜像与 kubelet 目录迁到数据盘 | 预防 | @b | 9-05 |
| 把这三项加进节点上线检查清单 | 制度 | @a | 8-22 |
```

<Callout type="tip" title="每次复盘至少产出一条「制度类」改进">
只修当前这个问题，同类问题还会在别的节点、别的集群上重演。

上面那张表里最后一行才是真正防止复发的那条：**把改进沉淀进上线检查清单**。这样新节点、新集群天生就带着这次事故的教训。

一个可操作的标准：复盘的改进项里如果没有一条是修改清单、模板或准入策略的，这次复盘就还没做完。
</Callout>

### 时间线要用数据还原

上面那份复盘里的 `01:48 DiskPressure` 是从**采集的 Event** 里查到的 —— 而 K8s Event 默认只在 etcd 里留 1 小时（L3《可观测性》讲过）。

没有采集 Event 的集群，复盘时只能靠人回忆「大概两点左右开始的」，而**最关键的那 18 分钟预警窗口就永远发现不了**。

这是「采集 Event 到日志系统」这件小事的真实价值。

## 沉淀与交接

三份文档，缺一份交接就不完整：

| 文档 | 内容 | 更新时机 |
| --- | --- | --- |
| **集群档案** | 拓扑、网段、版本、组件清单、各种凭据在哪 | 每次变更 |
| **值班手册** | 按症状组织的 SOP 索引 | 每次事故后 |
| **上线检查清单** | 节点上线、集群交付的逐项检查 | 每次复盘后 |

集群档案的核心是回答「这套集群和别的有什么不一样」：

```markdown
# k8s1.zw1 集群档案

版本        v1.31.4，kubespray 2.31.0
控制面      mn-192-168-3-{21,22,23}，VIP 192.168.3.101（kube-vip）
网段        节点 192.168.3.0/24 | Pod 172.24.0.0/13 (/24 每节点，上限 2048)
            Service 172.23.0.0/16
CNI         Cilium，kubeProxyReplacement，k8sServiceHost=127.0.0.1
存储        ceph-csi-rbd (block-nvme) + gpfs-csi (gpfs-fs1)
GPU         8 台 H100 八卡，Kueue 配额 64 卡 ← 【扩容后必须同步更新】
特殊约定    · etcd 配额已调至 8GB
            · containerd_discard_unpacked_layers=false（Spegel 依赖）
            · addons 全部由 helmwave 独立管理，仅 kube-vip 由 kubespray 装
配置仓库    git@…/k8s1-zw1-inventory
凭据        etcd 备份加密密钥在 vault://…
```

<Callout type="warn" title="「特殊约定」这一节是交接时最值钱的部分">
这一节记的是那些**违反直觉、但有原因**的配置。它们的共同特点是：不知道原因的人会认为是错的，然后「顺手改回来」。

比如 `containerd_discard_unpacked_layers=false` 看起来是在浪费磁盘，接手的人很可能把它改成 `true` —— 然后 Spegel 的 P2P 静默失效，几个月后某次大规模拉镜像时才暴露。

**每条特殊约定都要写明原因和影响**。这是交接文档里唯一无法从集群现状反推出来的信息。
</Callout>

## 这一节的落点

- **P1 告警每周 ≤ 3 条**是告警质量的硬指标；没人处理过的告警该降级
- SOP 五部分：含义、影响、**逐条可复制的诊断命令**、处置、**「不要做」**
- 值班手册按**症状**组织，不按组件 —— 值班的人拿到的是症状
- 「出问题就回滚」不是方案；要写清命令、耗时、是否丢数据、**回滚边界在哪**
- 复盘要问「**为什么没提前发现**」，且至少产出一条**制度类**改进
- 时间线用采集的 Event 还原 —— 这是采集 Event 这件小事的真实价值
- 交接文档里最值钱的是**「特殊约定」**：那些看起来错、其实有原因的配置
