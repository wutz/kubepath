kubelet 自己不跑容器。它把「起一个容器」这件事通过 CRI 交给 containerd，containerd 再交给 runc。

这条链路有三段，任何一段断了，现象都是「节点 NotReady」或者「Pod 卡在 ContainerCreating」。所以排障时得知道自己在看哪一段。

## 完整调用链

```
kubelet
  │  gRPC over unix socket
  │  /run/containerd/containerd.sock
  ▼
containerd ──── CRI plugin（实现 RuntimeService / ImageService）
  │
  ├─ 镜像：拉取、解包成 snapshot（OverlayFS 层）
  └─ 容器：创建 task
        │  shim 进程，每个 Pod 一个
        ▼
   containerd-shim-runc-v2
        │
        ▼
      runc ──── 真正调 clone()、设 namespace、写 cgroup，然后 exec 用户进程
```

CRI 只有两个服务：

| 服务 | 管什么 | kubelet 什么时候调 |
| --- | --- | --- |
| **RuntimeService** | sandbox 与容器的增删查、exec、日志 | 创建 Pod、探针、`kubectl exec` |
| **ImageService** | 镜像拉取、列举、删除、磁盘统计 | 起容器前拉镜像、磁盘压力时回收 |

<Callout type="note" title="为什么要有 shim 这一层">
`runc` 是个「跑完就退出」的命令行工具 —— 它设置好 namespace 和 cgroup，exec 用户进程，然后自己退出。那谁来当容器进程的父进程、收它的退出码？

这就是 shim 的作用。每个 Pod 一个 shim 进程，它常驻，持有容器的 stdio 和退出状态。好处是 **containerd 自己可以重启而不杀掉容器** —— 升级 containerd 不会导致业务中断。这也是为什么 `systemctl restart containerd` 通常是安全的，而 `systemctl restart kubelet` 也一样。
</Callout>

## dockershim 之前与之后

这条链路曾经更长。1.24 之前，如果节点用的是 Docker，kubelet 要先经过一段叫 **dockershim** 的翻译代码：

```
1.24 之前（Docker 节点）
kubelet → dockershim → dockerd → containerd → shim → runc
                        ↑
                两个多余的跳数，且 dockerd 一重启，链路就断

1.24 之后
kubelet → CRI → containerd → shim → runc
```

dockerd 从来不实现 CRI —— 它有自己的 API，于是 kubelet 里得内置一段专门伺候它的适配层。这段代码由 K8s 维护、随 kubelet 发版，成本高、故障面大，最终在 1.24 被删掉。

要留意的是**删掉的是那段适配层，不是 Docker 生态**：

- containerd 本来就是 Docker 公司拆分捐出的组件，两者是同一条链路的上下段，不是竞品
- 镜像格式是 OCI 标准，`docker build` 出来的镜像 containerd 直接能跑，这一层从未变过
- 变的只是**节点上不再需要 dockerd**，因此也就没有 `docker` 命令可用

## pause 容器与 Pod sandbox

每个 Pod 起来时，第一个被创建的容器不是你写的那个，而是 **pause**：

```bash
crictl pods                       # 看 sandbox
crictl ps -a                      # 看容器
ps -ef | grep pause               # 宿主机上能看到 pause 进程
```

pause 容器什么都不干，它的存在只为一件事：**持有 namespace**。

```
Pod sandbox（pause 容器）
  ├─ network namespace  ← Pod IP 挂在这里
  ├─ ipc namespace
  └─ uts namespace
       ▲
       │ 业务容器 join 进来，共享上面这几个 namespace
       │
  ┌────┴────┬─────────┐
  容器 A    容器 B    initContainer
```

这解释了 L0《容器到底是什么》留下的那个问题：同 Pod 内的容器为什么能 `localhost` 互访 —— 它们 join 了同一个 pause 容器的 network namespace。也解释了为什么**业务容器反复重启，Pod IP 却不变**：IP 属于 sandbox，业务容器重启不重建 sandbox。

<Callout type="warn" title="sandbox 没起来，看的地方不一样">
`kubectl describe pod` 里如果看到 `FailedCreatePodSandBox`，那问题在 **CNI**，不在你的镜像或命令 —— sandbox 的网络是 CNI 插件配的。

典型报错：`failed to setup network for sandbox ... plugin type="cilium-cni" failed`。这时候去查 CNI 的 DaemonSet、节点上 `/etc/cni/net.d/` 的配置文件，以及 IP 地址池有没有耗尽，而不是去查业务镜像。
</Callout>

## crictl：kubectl 看不到的时候用它

`kubectl` 走 apiserver，节点失联时就用不了了。`crictl` 直接和节点上的 containerd 说话，是节点侧排障的主力：

```bash
# crictl 需要指定 endpoint，或者写进 /etc/crictl.yaml 一次配好
cat > /etc/crictl.yaml <<'EOF'
runtime-endpoint: unix:///run/containerd/containerd.sock
image-endpoint: unix:///run/containerd/containerd.sock
timeout: 10
EOF

crictl ps -a                       # 所有容器，含已退出的
crictl pods                        # 所有 sandbox
crictl logs <container-id>         # 容器日志（kubectl logs 拿不到时用）
crictl inspect <container-id>      # 完整配置：cgroup 路径、挂载、环境变量、PID
crictl images                      # 节点上的镜像
crictl imagefsinfo                 # 镜像占用的磁盘
crictl stats                       # 实时资源占用
```

<Callout type="tip" title="containerd namespace ≠ K8s namespace">
containerd 自己有一套 namespace，用来隔离不同调用方的容器与镜像 —— 和 K8s 的 Namespace 对象**完全是两回事**，只是重名。

kubelet 建的所有东西都在 `k8s.io` 这个 containerd namespace 下：

```bash
ctr namespaces ls
# NAME    LABELS
# default            ← ctr / nerdctl 默认看这里，通常是空的
# k8s.io             ← Pod 的容器和镜像都在这
# moby               ← 如果这台机器上还装了 dockerd，它用这个
```

`crictl` 不需要操心这件事 —— 它只认 K8s 那一套。`ctr` 和 `nerdctl` 则必须显式带 `-n k8s.io`，否则会得出「节点上什么都没跑」的错误结论。
</Callout>

## 节点上的三个客户端：crictl、nerdctl、ctr

节点上没有 `docker` 命令（1.24 之后不需要 dockerd），取而代之的是三个层次不同的工具：

| 工具 | 来自 | 面向 | 什么时候用 |
| --- | --- | --- | --- |
| **crictl** | Kubernetes SIG-Node | CRI 语义：sandbox / 容器 / 镜像 | **节点排障的默认选择**，输出和 kubectl 对得上 |
| **nerdctl** | containerd 项目 | Docker 兼容 CLI | 要 `build` / `run` / `compose` 那套手感时 |
| **ctr** | containerd 自带 | 最底层的调试接口 | 前两个都拿不到信息时的兜底 |

三者的常用命令对照：

| 目的 | crictl | nerdctl（带 `-n k8s.io`） | ctr（带 `-n k8s.io`） |
| --- | --- | --- | --- |
| 列容器 | `crictl ps -a` | `nerdctl ps -a` | `ctr containers ls` |
| 列 Pod / sandbox | `crictl pods` | 不区分 | 不区分 |
| 看日志 | `crictl logs <id>` | `nerdctl logs <id>` | 不支持 |
| 进容器 | `crictl exec -it <id> sh` | `nerdctl exec -it <id> sh` | `ctr tasks exec` |
| 列镜像 | `crictl images` | `nerdctl images` | `ctr images ls` |
| 拉镜像 | `crictl pull <img>` | `nerdctl pull <img>` | `ctr images pull` |
| 构建镜像 | 不支持 | `nerdctl build`（需 buildkit） | 不支持 |

```bash
# 同一台节点上，三种视角看同一批容器
crictl ps
nerdctl -n k8s.io ps
ctr -n k8s.io containers ls
```

<Callout type="warn" title="ctr 是「不带保险」的工具">
`ctr` 直接操作 containerd，**不经过 CRI，也不通知 kubelet**。用它删掉一个容器，kubelet 会认为容器意外退出并按策略重建 —— 轻则重启，重则让排障现场消失。

它的正确用途只有两类：看 containerd 自身的状态（namespace、snapshot、内容寻址存储），以及 crictl 也失灵时确认 containerd 还活着。**任何写操作都别用它。**
</Callout>

<Callout type="tip" title="nerdctl 在节点上最实用的两个场景">
1. **验证私有仓库的凭据与网络** —— `nerdctl -n k8s.io pull harbor.internal/team/app:v1` 能带上 `--insecure-registry` 之类的参数逐个试，比反复改 Pod 重试快得多
2. **临时起一个诊断容器** —— `nerdctl -n k8s.io run --rm -it --net host nicolaka/netshoot bash`，不占用 K8s 的资源账，也不会被调度器和探针干扰

需要注意的是：这样起的容器 kubelet 不知道它的存在，用完记得清掉。
</Callout>

## cgroup 驱动必须两边一致

kubelet 和 containerd 都要往 cgroup 里写限制，两者必须用同一个驱动。不一致的后果是资源限制静默失效或容器起不来。

```bash
# containerd 侧：/etc/containerd/config.toml
# runc.options 里的 SystemdCgroup（这个文件里通常有多处，要全改）
grep -n SystemdCgroup /etc/containerd/config.toml
```

kubespray 里对应一个变量：

```yaml
# inventory/mycluster/group_vars/all/containerd.yml
containerd_use_systemd_cgroup: true    # 默认 true，即 systemd 驱动
```

> 从 K8s 1.31 起 kubelet 会自动探测 CRI 的 cgroup 驱动，后续版本会废弃 kubelet 的 `cgroupDriver` 参数 —— 也就是说 1.31 之后不需要在 kubelet 侧再配一遍了。

<Callout type="trap" title="systemctl daemon-reload 会让 GPU Pod 失去设备权限">
这是一个真实踩过的坑，现象非常迷惑：GPU Pod 跑得好好的，在宿主机上执行了一次 `systemctl daemon-reload`，Pod 里 `nvidia-smi` 就开始报 `Failed to initialize NVML: Unknown Error`。

原因：systemd cgroup 驱动下，`daemon-reload` 会重建容器的 cgroup，导致容器丢失 NVIDIA 设备的访问权限。

关键在于**哪些 Pod 会中招**：正常用 `resources.limits.nvidia.com/gpu` 申请 GPU 的 Pod 不会 —— gpu-operator 从 22.9.2 起通过注入设备软链接解决了。中招的是那种**不申请 GPU 资源、直接设 `NVIDIA_VISIBLE_DEVICES=all`** 的 Pod，它走不到那段修复逻辑。

短期方案是把 containerd 切成 `cgroupfs` 驱动（`containerd_use_systemd_cgroup: false`，gpu-operator 的 `nvidia-container-toolkit-daemonset` 会读这个设置去配 nvidia runtime）。长期方案是用 DRA 做跨 Pod 的 GPU 共享。

**更省事的做法是从规范入手**：要求所有 GPU Pod 必须用 `resources.limits` 申请卡，禁止 `NVIDIA_VISIBLE_DEVICES=all`。这条规范本身还顺带解决了 GPU 资源被超卖的问题。
</Callout>

## 镜像拉取失败的四类原因

`ImagePullBackOff` 是最常见的故障之一，原因就那么几类，按这个顺序查最快：

| 类型 | describe 里的报错特征 | 查什么 |
| --- | --- | --- |
| 镜像不存在 | `manifest unknown` / `not found` | 镜像名和 tag 拼写、仓库里到底有没有 |
| 认证失败 | `unauthorized` / `authentication required` | `imagePullSecrets`、containerd 的 registry 配置 |
| 网络不通 | `dial tcp ... i/o timeout` | 节点到仓库的连通性、代理、DNS |
| 证书问题 | `x509: certificate signed by unknown authority` | 私有仓库的 CA 是否装到节点上 |

```bash
# 绕开 K8s，直接在节点上验证 —— 能立刻区分「集群配置问题」和「节点到仓库的问题」
crictl pull <image>
```

## 这一节的落点

- kubelet → CRI → containerd → shim → runc，**四段链路，排障先定位在哪一段**
- dockershim 移除的是那段适配层，**不是 Docker 生态** —— containerd 本就是 Docker 拆出来的，镜像也一直通用
- pause 容器持有 namespace，所以业务容器重启 Pod IP 不变，`FailedCreatePodSandBox` 指向 CNI
- 节点侧默认用 `crictl`，要 docker 手感用 `nerdctl -n k8s.io`，`ctr` 只读不写
- cgroup 驱动两边必须一致；GPU Pod 必须用 `resources.limits` 申请卡，别用 `NVIDIA_VISIBLE_DEVICES=all`
- `crictl pull` 能一步区分「集群配置问题」和「节点到仓库的问题」
