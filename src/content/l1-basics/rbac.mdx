「谁能动这个集群、能动到什么程度」——交付前必须回答清楚。交付后再补就是一场大手术：你得逐个找出现有的调用方，猜他们到底用了哪些权限，收紧之后等着谁来报错。

## 认证与授权是两个独立阶段

一个请求进 apiserver 要过三道门：

```
请求
  │
  ├─ 1. 认证（Authentication）  你是谁？
  │      证书 / Bearer Token / OIDC
  │      失败 → 401 Unauthorized
  │
  ├─ 2. 授权（Authorization）   你能做这个吗？
  │      RBAC（还有 Node、Webhook 等模式）
  │      失败 → 403 Forbidden
  │
  └─ 3. 准入（Admission）       这个对象合规吗？要不要改写？
         Mutating → Validating
         失败 → 报错，带上具体的策略名
```

**401 和 403 指向完全不同的问题**：401 是身份没认出来（证书过期、token 无效），403 是身份认出来了但没权限（RBAC 缺规则）。看错这一点会白查很久。

<Callout type="note" title="K8s 里没有「用户」这个对象">
这是个反直觉的设计：`kubectl get users` 是不存在的。

K8s **不管理人**。它只认证：证书里的 `CN` 字段就是用户名，`O` 字段就是用户组；OIDC token 里的某个 claim 就是用户名。用户是外部概念，K8s 只在请求到来时读取身份信息。

有实体对象的只有 **ServiceAccount** —— 那是给集群内的程序用的。

所以「给某个人开权限」的实际操作是两选一：给他签一张客户端证书，或者建一个 ServiceAccount 把 token 给他。后者好管理得多（可以随时删掉、不需要 CA、不涉及证书有效期），这也是下面推荐的做法。
</Callout>

## ServiceAccount：集中管理人员权限

给人开权限时，把所有 ServiceAccount 统一放在一个专用命名空间里管理 —— 比如 `sa-management`。好处是权限清单一目了然，审计和回收都在一个地方。

```bash
kubectl create ns sa-management
kubectl -n sa-management create sa harbor-developer
```

从 K8s 1.24 起，创建 ServiceAccount **不再自动生成永久 token**，要显式建：

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: harbor-developer
  namespace: sa-management
  annotations:
    kubernetes.io/service-account.name: harbor-developer
type: kubernetes.io/service-account-token
```

```bash
kubectl get secret -n sa-management harbor-developer -o jsonpath="{.data.token}" | base64 -d
```

<Callout type="warn" title="两种 token，用途不要混">
| | 长期 Secret token | 投射 token（projected） |
| --- | --- | --- |
| 有效期 | **永不过期** | 有 TTL，kubelet 自动轮转 |
| 用途 | 给**人**或集群外的系统用 | 给**集群内的 Pod** 用 |
| 风险 | 泄漏后一直有效，只能靠删 Secret 撤销 | 过期自动失效 |

Pod 里挂载的 SA token 默认已经是投射 token（1.22+），这是对的，别改。

而给人用的长期 token 要当成密码对待：走密码管理器发放，记录发给了谁，人员离职时删掉对应的 Secret。**不要提交进 Git，不要贴在聊天工具里。**
</Callout>

## Role 与 ClusterRole：作用域的差别

判断该用哪个，看资源是不是 namespaced：

```bash
kubectl api-resources

# NAME              SHORTNAMES   APIVERSION           NAMESPACED   KIND
# configmaps        cm           v1                   true         ConfigMap
# namespaces        ns           v1                   false        Namespace
# storageclasses    sc           storage.k8s.io/v1    false        StorageClass
```

- `NAMESPACED=true` 的资源 → 用 **Role**
- `NAMESPACED=false` 的资源（Node、PV、StorageClass、Namespace 本身）→ 必须用 **ClusterRole**

`apiGroups` 怎么填也从这张表读：

| APIVERSION | apiGroups 写什么 |
| --- | --- |
| `v1` | `""`（core 组，空字符串） |
| `apps/v1` | `"apps"` |
| `storage.k8s.io/v1` | `"storage.k8s.io"` |

<Callout type="trap" title="apiGroups 填错是 403 的头号原因">
把 Pod 写进 `apiGroups: ["apps"]`，或者把 Deployment 写进 `apiGroups: [""]` —— 规则语法完全合法，apply 也不会报错，但**永远不会匹配任何请求**。

排查时用这个命令，它直接给出结论而不是让你读 YAML：

```bash
kubectl auth can-i get pods --as=system:serviceaccount:sa-management:harbor-developer -n harbor
kubectl auth can-i --list --as=system:serviceaccount:sa-management:harbor-developer -n harbor
```
</Callout>

## 四种绑定组合

Role/ClusterRole 定义「能做什么」，Binding 决定「谁能做，在哪能做」：

| 组合 | 效果 |
| --- | --- |
| Role + RoleBinding | 在**该 RoleBinding 所在的命名空间**内生效 |
| ClusterRole + RoleBinding | **把集群角色限定到单个命名空间** ← 最常用 |
| ClusterRole + ClusterRoleBinding | 全集群生效 |
| Role + ClusterRoleBinding | **无效组合**，不要用 |

第二种是实践中最有价值的：复用内置的 ClusterRole，但把范围限死在一个命名空间。

```yaml
# 让某人在 harbor 命名空间里有编辑权
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: harbor-developer
  namespace: harbor                    # ← 权限只在这个命名空间生效
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: edit                           # 内置角色，不用自己写
subjects:
  - kind: ServiceAccount
    name: harbor-developer
    namespace: sa-management            # ← SA 本体在管理命名空间里
```

四个内置 ClusterRole 覆盖了大部分场景：

| 名字 | 权限 |
| --- | --- |
| `view` | 只读，且**看不到 Secret** |
| `edit` | 读写常规资源，不能改 RBAC |
| `admin` | `edit` + 能管理命名空间内的 RBAC |
| `cluster-admin` | 全部权限，慎用 |

## 一份实用的权限模板

给业务团队开权限，通常需要三块：

```yaml
# 1. 命名空间内的编辑权（用内置 edit）—— 见上面的 RoleBinding

# 2. 集群级的命名空间列表权限：kubectx / kubie 这类工具需要它
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata: { name: namespace-viewer }
rules:
  - apiGroups: [""]
    resources: ["namespaces"]
    verbs: ["get", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata: { name: harbor-developer-ns-view }
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: namespace-viewer
subjects:
  - kind: ServiceAccount
    name: harbor-developer
    namespace: sa-management
```

第三块是节点与存储的只读权限（排障时要看 node 状态），按需给。

<Callout type="tip" title="用 kustomize 把一个人的权限打成一个包">
一个人的权限涉及 SA、Secret、RoleBinding、ClusterRoleBinding 四五个对象。散着放，回收时必然漏。

```bash
kubectl apply -k harbor-developer     # 一个目录 = 一个人的完整权限
kubectl delete -k harbor-developer    # 离职时一条命令收回
```
目录进 Git，权限变更就有了 review 和历史记录 —— 这比在集群里手工 patch 可靠得多。
</Callout>

## 签发 kubeconfig

```yaml
apiVersion: v1
clusters:
  - name: k8s1-zw1
    cluster:
      server: https://10.128.0.10:6443
      certificate-authority-data: <集群 CA 的 base64>
contexts:
  - name: k8s1-zw1
    context:
      cluster: k8s1-zw1
      namespace: harbor           # 默认命名空间，省得每次敲 -n
      user: harbor-developer
current-context: k8s1-zw1
kind: Config
users:
  - name: harbor-developer
    user:
      token: <前面拿到的 token>
```

<Callout type="warn" title="别用 insecure-skip-tls-verify">
模板里图省事写 `insecure-skip-tls-verify: true` 很常见，但它关掉了对 apiserver 身份的校验 —— 中间人可以冒充 apiserver，把用户的 token 收走。而这个 token 是永久有效的。

正确做法是把集群 CA 填进去：

```bash
kubectl config view --raw --minify -o jsonpath='{.clusters[0].cluster.certificate-authority-data}'
```
多打一条命令的事，换来的是这份 kubeconfig 可以放心发出去。
</Callout>

## 最小权限：几条能落地的规则

1. **默认给 `view`，按需升级** —— 而不是先给 `edit` 再想着收紧（收紧永远不会发生）
2. **绝不发 `cluster-admin`** —— 需要集群级权限就精确列资源和 verb
3. **`*` 是危险信号** —— `verbs: ["*"]` 或 `resources: ["*"]` 出现在 review 里就该被质疑
4. **警惕权限提升路径** —— 能创建 Pod 就能挂载任意 SA 的 token，能改 RoleBinding 就能给自己提权。所以 `edit` 不含 RBAC 权限是刻意的
5. **定期审计** ——

```bash
# 谁有 cluster-admin
kubectl get clusterrolebindings -o json | \
  python3 -c "
import json,sys
for b in json.load(sys.stdin)['items']:
    if b['roleRef']['name']=='cluster-admin':
        for s in b.get('subjects') or []:
            print(b['metadata']['name'], '→', s['kind'], s.get('namespace',''), s['name'])
"
```

## 这一节的落点

- **401 是认证，403 是授权** —— 方向完全不同，先分清再查
- K8s 不管理人，给人开权限用 ServiceAccount，统一放在 `sa-management` 里
- 1.24 之后长期 token 要显式创建；它**永不过期**，当密码对待
- 看 `kubectl api-resources` 决定 Role 还是 ClusterRole，以及 `apiGroups` 怎么填 —— 填错是 403 的头号原因
- **ClusterRole + RoleBinding** 是最有用的组合：复用内置角色，作用域限死
- 用 `kubectl auth can-i` 验证，别靠读 YAML 推断
- kubeconfig 里填 CA，不要用 `insecure-skip-tls-verify`
