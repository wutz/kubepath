整条路线从这里开始，而且是直接上手：写一个 Dockerfile、构建出镜像、跑起来、进去看一眼、把日志捞出来。容器在内核里到底是什么，下一节《容器到底是什么》再拆 —— 先有手感，那些机制才有东西可以挂靠。

为什么在一门 K8s 教程里还讲 Docker？因为**镜像是 K8s 唯一的交付物**。集群再熟，镜像做不好照样天天出事：拉不动、起不来、跑起来是 root、改一行代码重新构建要八分钟。而这些手感，用 Docker 练最快。

## docker run 背后发生了什么

```bash
docker run -d --name web -p 8080:80 nginx:1.27-alpine
```

这一条命令做了五件事：

1. 本地没有 `nginx:1.27-alpine` 就去 registry 拉，逐层下载并解压到本地存储
2. 用这些只读层叠出一个 rootfs，最上面加一个可写层
3. 建一组 namespace（mnt / pid / net / uts / ipc）
4. 建 cgroup，把资源限制写进去
5. 在这套环境里 `exec` 镜像声明的启动进程

这五步里，第 2 步靠 OverlayFS，第 3、4 步靠 namespace 与 cgroup —— 三个名字下一节会逐个拆开。这里先记住结论：**Docker 本身不隔离任何东西，它只是把内核能力包装成了一条命令。**

## 日常命令地图

| 目的 | 命令 | 到了 K8s 里对应什么 |
| --- | --- | --- |
| 起一个容器 | `docker run` | `kubectl run` / Deployment |
| 看在跑什么 | `docker ps -a` | `kubectl get pod` |
| 看日志 | `docker logs -f web` | `kubectl logs -f` |
| 进去看看 | `docker exec -it web sh` | `kubectl exec -it` |
| 看完整状态 | `docker inspect web` | `kubectl describe pod` |
| 看资源用量 | `docker stats` | `kubectl top pod` |
| 拷文件进出 | `docker cp web:/etc/nginx/nginx.conf .` | `kubectl cp` |

这张对应表值得记住：**K8s 的排障命令几乎是 Docker 命令的分布式版本**，差别在于对象从「一台机器上的容器」变成了「集群里的 Pod」。

<Callout type="tip" title="排障顺序：logs → describe/inspect → exec">
不管在 Docker 还是 K8s，顺序都是一样的：先看进程自己说了什么（logs），再看平台说了什么（inspect / describe），最后才进容器里翻（exec）。

反过来做 —— 一上来就 `exec` 进去 —— 常见的结果是容器已经退出了，根本进不去。而这时候 `logs` 里那行退出原因一直躺在那儿。
</Callout>

## Dockerfile：每一行都是一层

```dockerfile
FROM golang:1.23-alpine AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download                      # 依赖单独一层，代码改动不会让它失效
COPY . .
RUN CGO_ENABLED=0 go build -o /out/app ./cmd/app

FROM alpine:3.20
RUN apk add --no-cache ca-certificates
COPY --from=build /out/app /usr/local/bin/app
USER 65532:65532                         # 非 root 运行
EXPOSE 8080
ENTRYPOINT ["/usr/local/bin/app"]
```

这份模板里有三个刻意的设计：

- **先 `COPY go.mod` 再 `COPY .`** —— 构建缓存按层命中，依赖层和代码层分开，改一行业务代码就不用重新拉依赖
- **多阶段构建** —— 编译工具链留在 `build` 阶段，最终镜像里只有一个二进制，从几百 MB 降到十几 MB
- **`USER` 非 root** —— K8s 里配 `runAsNonRoot: true` 的时候，镜像本身就得先具备这个条件

<Callout type="trap" title="ENTRYPOINT 用 shell 形式，SIGTERM 就送不到进程">
两种写法的差别不是风格问题：

```dockerfile
ENTRYPOINT /usr/local/bin/app        # shell 形式：实际是 /bin/sh -c "..."，PID 1 是 sh
ENTRYPOINT ["/usr/local/bin/app"]    # exec 形式：PID 1 就是你的进程
```

shell 形式下 PID 1 是 `sh`，它不会把 `SIGTERM` 转发给子进程。于是 `kubectl delete pod` 发出的优雅终止信号被吞掉，等满 30 秒被 `SIGKILL` 强杀 —— 表现就是「删 Pod 特别慢」「滚动更新期间总掉几个请求」。

**永远用 exec 形式（JSON 数组）写 ENTRYPOINT 和 CMD。**
</Callout>

## 镜像瘦身：为什么值得较真

镜像大小直接换算成集群里的三笔账：节点拉取时间、节点磁盘占用、扩容响应速度。一个 1.2G 的镜像在一个 50 节点的集群里滚动一次，是 60G 的网络流量。

几条见效最快的：

```bash
# 1. 基础镜像选小的：alpine / distroless / scratch
# 2. .dockerignore 挡掉 .git、node_modules、本地构建产物
cat > .dockerignore <<'EOF'
.git
node_modules
dist
*.log
EOF

# 3. 合并 RUN 并在同一层清理缓存 —— 分层写清理是无效的
RUN apt-get update && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/*

# 4. 看清楚每一层多大
docker history myapp:v1 --no-trunc
```

<Callout type="warn" title="分层删除删不掉体积">

```dockerfile
RUN wget https://example.com/big.tar.gz   # 这一层 +800MB
RUN rm big.tar.gz                          # 这一层删掉了，但 800MB 还在镜像里
```

镜像层是只读叠加的，后一层的删除只是在上层做了个「白障」标记，底下那 800MB 依然要下载、依然占磁盘。**下载、解压、清理必须在同一个 `RUN` 里完成。**
</Callout>

## Docker、containerd 与 K8s 的关系

很多人以为 Docker 是一个整体的程序，其实 `docker run` 敲下去之后，请求要穿过四层：

```
docker CLI            你敲的命令，一个 HTTP 客户端
  │  REST over /var/run/docker.sock
  ▼
dockerd               Docker Engine 守护进程：镜像构建、网络、卷、compose 这些「上层功能」
  │  gRPC
  ▼
containerd            容器生命周期与镜像管理的核心
  │
  ▼
containerd-shim → runc   真正建 namespace、写 cgroup、exec 用户进程
```

**containerd 本来就是 Docker 拆出来的那一半** —— 2017 年 Docker 把容器运行时这一层独立成项目捐给 CNCF，自己保留上层的构建、网络、compose 那些开发者功能。所以两者不是竞品关系，而是同一条链路的上下两段。

这解释了一个常被误解的说法：

| 说法 | 实情 |
| --- | --- |
| 「K8s 弃用了 Docker」 | 弃用的是 **dockershim** —— kubelet 里那段专门适配 dockerd 的翻译代码 |
| 「Docker 造的镜像 K8s 不认了」 | 镜像是 OCI 标准，一直通用。Docker 构建、containerd 运行完全没问题 |
| 「本地开发也不能用 Docker 了」 | 完全能用。构建、调试、compose 这些场景 Docker 依然最顺手 |

K8s 1.24 移除 dockershim 之后，kubelet 直接通过 CRI 和 containerd 对话，中间少了 dockerd 这一跳 —— 少一个守护进程、少一层翻译。链路细节在 L1《运行时与 CRI》展开。

<Callout type="note" title="生产节点上没有 docker 命令，怎么办">
装好的生产集群节点上通常只有 containerd，没有 dockerd，也就没有 `docker` 命令。这时候有三个客户端可选：

- **`crictl`** —— 按 CRI 语义设计，看 Pod / sandbox / 容器，是节点排障的主力
- **`nerdctl`** —— containerd 官方的 Docker 兼容 CLI，命令几乎一一对应
- **`ctr`** —— containerd 自带的底层调试工具，功能最原始

日常排障用 `crictl`；需要 `docker` 那套手感（build、run、compose）时用 `nerdctl`。三者的分工在 L1《运行时与 CRI》里有对照表。
</Callout>

## nerdctl：把 docker 的手感带到 containerd 上

[nerdctl](https://github.com/containerd/nerdctl) 是 containerd 项目自己维护的 CLI，设计目标就是**和 docker 命令兼容**。上面练的那些命令，绝大多数原样就能用：

```bash
nerdctl run -d --name web -p 8080:80 nginx:1.27-alpine
nerdctl ps -a
nerdctl logs -f web
nerdctl exec -it web sh
nerdctl build -t demo-api:v1 .          # 需要 buildkit
nerdctl compose up -d                    # compose 也支持
```

熟悉之后可以直接 `alias docker=nerdctl`，肌肉记忆完全不用改。

它相比 docker 还多了几样 K8s 场景用得上的东西：镜像懒加载（lazy-pulling，大镜像可以边拉边跑）、镜像加密、以及原生的 rootless 模式。

<Callout type="warn" title="nerdctl 在节点上要带 --namespace k8s.io">
containerd 用 namespace 隔离不同调用方的资源，K8s 的容器和镜像都在 `k8s.io` 这个 namespace 下，而 nerdctl 默认用 `default`。

```bash
nerdctl ps                        # 空的 —— 看的是 default namespace
nerdctl --namespace k8s.io ps     # 这才是 Pod 里的容器
nerdctl -n k8s.io images          # 节点上 K8s 用的镜像
```

忘了这个参数，就会得出「节点上什么都没跑」的错误结论。这也是节点排障优先用 `crictl` 的原因之一 —— 它只看 K8s 的那个 namespace，不会认错地方。
</Callout>

<Callout type="note" title="哪些概念能带进 K8s，哪些不能">
**能带过去的**：镜像与分层、ENTRYPOINT/CMD、环境变量、挂载卷、资源限制 —— 这些在 K8s 里都有一一对应的字段。

**带不过去的**：`docker run` 的一次性心智（K8s 是声明式的，你描述期望状态而不是执行动作）、`--link` 与 docker 自带网络（K8s 有自己的网络模型）、`docker-compose` 的编排语义（对应 Deployment + Service，但调度、扩缩、自愈完全不同）。
</Callout>

## 这一节留下的三条习惯

1. **exec 形式写 ENTRYPOINT** —— 一行改动，换掉一整类优雅终止问题
2. **多阶段构建 + 非 root 用户** —— 镜像既小又能过 K8s 的安全策略
3. **排障顺序固定：logs → inspect → exec** —— 这个顺序到了 K8s 一模一样，只是命令换成 kubectl
